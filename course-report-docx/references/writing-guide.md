## 通用结构

先确认一件事：**课程或老师是否给了指定章节结构**。给了就严格照办，本文件只作补充；没给，就按下面这套骨架组织。

| 章 | 作用 | 建议篇幅占比 |
|---|---|---|
| 封面 / 摘要 / ABSTRACT / 目录 | 前置部分，不计入正文章节编号 | — |
| 第 1 章 绪论 | 回答"为什么做" | 15% |
| 第 2 章 主体技术内容 | 回答"做什么、怎么做"（需求、设计、建模） | 40% |
| 第 3 章 实现与验证 | 回答"做成啥样"（实现、测试、结果） | 30% |
| 第 4 章 结束语 | 总结与展望 | 5% |
| 参考文献 | — | — |

写作顺序建议**先搭标题骨架再填内容**。先把三级标题列全，检查逻辑是否连贯、有没有重叠或遗漏，再逐节写正文——比边想边写、写完再发现章节错位要省力得多。

## 摘要

摘要是整篇文章的门面。评审老师通常先看摘要，摘要写得空泛，后面写得再好也会被低估。

**用回答问题的方式自查这五问**：

1. **为什么要做？** —— 背景与意义，一到两句
2. **做些什么？** —— 研究/设计内容，明确交代交付了什么系统或方案
3. **困难在哪里？** —— 关键点，也就是本文的创新点或技术难点
4. **如何去做？** —— 方法和工具
5. **做成啥样？** —— 目标和结论，有数据就给数据

**写法要点**

- 摘要是一段完整的短文，不要分条列点
- 用第三人称陈述，不要出现"我""我们"
- 不要出现图表编号、参考文献序号、公式编号
- 中文摘要与英文摘要必须**内容对应**，不要各写各的
- 关键词 3~5 个，按重要性排序，选用能反映本文技术特征的术语，不要用"系统""设计"这类无区分度的泛词

## 第 1 章 绪论

本章回答"为什么做"，是引出后续设计的关键。

### 1.1 选题背景和研究意义

- 从行业或业务的真实痛点切入，落到本课题要解决的具体问题
- 背景要**正面阐述**，不要写成大段行业报告摘抄
- 意义要分层次：对业务/管理的意义，对技术的意义
- 有调研数据、政策依据、实际案例的，尽量引用并标注参考文献

### 1.2 文献综述（研究现状）

综述是研究的基础。要**总结、归类、继承**前人的工作，而不是罗列摘要。

写的时候可以按技术路线分组，每组交代：这类方法解决了什么、局限在哪、本文与它的关系。

三种典型错误要避免：

| 错误 | 表现 | 为什么不行 |
|---|---|---|
| 抄袭 | 把他人文章大段"移植"过来 | 文献综述不等于文献移植，这是诚信问题 |
| 张冠李戴 | 拼凑完文字后随手加几个引用标注 | 引用必须对应正确出处，这是对他人劳动的基本尊重 |
| 指鹿为马 | 论文写到参考文献部分才开始"设计"参考文献 | 引用应来自实际阅读过的文献，不能事后编造 |

### 1.3 论文组织结构

- 第一段整体介绍论文架构与行文脉络，告诉读者全文怎么展开
- 后续段落按章简要说明每章内容，一章一句或两句
- 这一节要能当"导读"用：读者看完就知道该跳到哪里看什么

## 第 2 章 主体技术内容

这一章因课题而异，但通用要求是一致的：

- **需求要可验证**。功能需求写成"系统能够……"的句式，避免"界面友好""性能优越"这类无法验收的描述；非功能需求尽量给数值指标（并发量、响应时间、数据量）
- **设计要画图**。结构、流程、数据模型都用图表达，图必须有编号和名称，并在正文中引用
- **建模要给出依据**。E-R 图、类图、表结构之间要能对上——实体对应表、属性对应字段、联系对应外键或关联表，这些对应关系要写清楚
- **取舍要讲理由**。为什么选这个方案、放弃另一个，哪怕只是一句话，也比直接给结论有说服力

---

## 第 3 章 实现与验证

- **实现**：只贴核心算法或关键代码，代码用算法框承载并给编号；完整代码放附录或仓库，正文不放
- **测试**：给出测试用例表（输入、预期输出、实际输出、结论），用例要覆盖正常路径和边界/异常路径
- **结果**：有数据就上图表，并对图表做解读——"图3-1显示……，说明……"，不要让读者自己猜

---

## 第 4 章 结束语

### 4.1 本文总结

- 再次概括完成了什么工作、解决了什么问题
- 再次强调创新点
- 说明研究成果的意义和本人的收获

注意：总结不是摘要的复制粘贴。摘要面向"要不要读下去"，总结面向"读完之后确认收获"。

### 4.2 工作展望

- 说明当前工作的**局限**（有什么没做、做的哪里不够好）
- 提出下步工作的规划和学习计划
- 有局限并不可怕，看不出局限才是问题

## 参考文献

- 文献要**真的读过**，且与正文引用位置对应
- 著录格式按 `format-spec.md` 第十四节的示例执行，注意文献类型标识：`[J]` 期刊、`[M]` 专著、`[D]` 学位论文、`[N]` 报纸、`[C]` 论文集
- 中文文献用中文标点，英文文献用半角标点，不要混用
- 数量上，课程设计报告一般 10~20 篇，其中外文文献建议不少于 2~3 篇，且尽量包含近 3~5 年的文献

## 图表公式在正文中怎么用

这一节说的不是格式，而是**图表与正文的配合**。

- **先文后图**。正文先提到图，图再出现。不要出现一张没有任何正文引用的"孤儿图"
- **引用要带编号**，用交叉引用（`如图2-1所示`），不要写成"如下图所示"——后者在文档调整后容易出错且无法定位
- **图表要能独立读懂**。题注要写清"这张图/表在说什么"，而不仅仅是编号
- **有数据图就要有解读**。不要贴完图就结束，至少解释趋势、对比或异常
- **公式要服务于推导**。只放正文需要引用的关键公式，并说明每个符号的含义

## 常见失分点

| 失分点 | 说明 |
|---|---|
| 摘要空泛 | 通篇"设计并实现了……系统"，没有交代难点与结果 |
| 标题层级混乱 | 用加粗大字冒充标题，导致无法生成自动目录 |
| 图表编号手工维护 | 增删一张图后全文编号错位 |
| 文献综述变成文献罗列 | 只列"某某提出了某某方法"，没有归纳与评述 |
| 只有成功路径的测试 | 测试用例表看不出异常处理能力 |
| 代码整段粘贴 | 正文成了代码仓库，缺少设计与解释 |
| 格式残留 | 忘记删除模板的红色说明文字、批注与修订痕迹 |
| 页眉/页码错误 | 摘要有页码、正文页码不从 1 开始、目录用阿拉伯数字 |
